# 对象集服务限制（Object Set Service limitations）

> 本文为 [Palantir 官方文档](https://www.palantir.com/docs/foundry/ontologies/oss-limitations/)的非官方中文翻译，仅供学习参考。原文 © 2026 Palantir Technologies Inc. 保留所有权利。

对象集服务（Object Set Service，OSS）是负责从本体查询和检索对象的服务。OSS 使用分层执行策略来平衡性能与规模，根据查询的大小和复杂度自动选择最优方式。

本页说明 OSS 如何处理不同规模的查询，以及在处理对象集时你应当了解的限制。

## 查询执行策略

OSS 使用分层执行策略，自动选择处理查询的最优方式：

1. **下推到存储层：** 对于简单查询，OSS 将操作直接下推到存储层，以利用已编入索引的数据结构。这是最快的执行路径，所需的计算开销最小。
2. **内存执行：** 对于包含更复杂操作的查询，OSS 会将数据加载到内存中进行快速处理，上限为一定容量。这最适合中等规模的查询。
3. **基于 Spark 的执行：** 对于超出内存容量的大规模查询，OSS 会自动回退到基于 Spark 的分布式计算。这使得处理大得多的对象集成为可能，但代价是额外的延迟和计算用量。

这些执行策略之间的切换是自动的，基于多个因素：

- **对象集大小：** 更大的对象集会触发 Spark 执行
- **查询复杂度：** 某些高级功能（派生属性、中间链接类型、接口环绕搜索（Search Around））无论规模大小都需要 Spark 执行
- **可用计算资源：** OSS 会平衡性能与资源利用率

在单个复杂查询中，OSS 可能会针对不同的执行阶段使用多种执行策略。理解每种方式的阈值和限制，将有助于你设计高效的查询并理解其性能特征。

**关键阈值：**

- **100,000 个对象（默认阈值）：** 对于环绕搜索和派生属性，从内存执行切换到基于 Spark 执行的阈值。
- **内部分页阈值：** 如果任何数据加载步骤需要从对象存储 v2 加载超过 25 页数据，OSS 会回退到 Spark。
- **10,000,000 个对象（默认阈值）：** 环绕搜索操作的最大结果集大小（叶子限制）。
- **100,000 个对象（默认阈值）：** 使用 `.all()` 或 `.allAsync()` 将对象加载到内存的上限（OSDK 限制；`getAllObjects` API 可以加载更多）。

### 执行策略对比

| 策略 | 何时使用 | 性能 | 计算成本 | 用例 |
| --- | --- | --- | --- | --- |
| **下推到存储** | 简单的筛选和聚合 | 最快 | 最低 | 可通过索引查找解析的基础查询 |
| **内存执行** | 对象集 ≤100,000 | 快 | 中等 | 大多数环绕搜索、中等规模查询 |
| **基于 Spark 的执行** | 对象集 >100,000 | 较慢（延迟更高） | 较高 | 大规模环绕搜索、复杂的多步骤查询 |

## 对象集大小限制

OSS 根据存储后端和操作类型实施不同的大小限制。这些限制确保了系统稳定性和可预测的性能。

### 对象存储 v1（Phonograph）[计划弃用]

> **⚠️ 注意：计划弃用**
>
> 对象存储 v1（Phonograph）处于开发的[计划弃用](https://www.palantir.com/docs/foundry/platform-overview/development-life-cycle/)阶段，将于 2026 年 6 月 30 日之后不可用。请[将你的对象类型和链接类型迁移](https://www.palantir.com/docs/foundry/object-backend/osv1-osv2-migration/)到对象存储 v2。

对象存储 v1 具有以下限制：

- **将对象加载到内存：** 在[对象函数（Functions on Objects）](https://www.palantir.com/docs/foundry/functions/overview/)中，使用 `.all()` 或 `.allAsync()` 方法最多可加载 **100,000 个对象**。
- **环绕搜索操作：** 当从对象集 A 向对象集 B 执行环绕搜索时，结果集（对象集 B）不能超过 **100,000 个对象**。

这些限制适用于对象存储 v1 中的所有操作。对于更大的查询，不会自动回退到基于 Spark 的执行。

### 对象存储 v2

对象存储 v2 通过其混合执行模型提供了更大的灵活性和规模：

- **内存执行：** 默认情况下，OSS 对不超过 **100,000 个对象**的对象集在内存中处理查询。
- **基于 Spark 的执行：** 当某个环绕搜索操作涉及超过 **100,000 个对象**时，OSS 会自动切换到基于 Spark 的分布式计算。
- **环绕搜索结果限制：** 来自环绕搜索操作的结果集（即从单个数据源加载的“叶子”对象集），在每次单独的环绕搜索操作中不能超过 **10,000,000 个对象**。此外，查询执行期间加载的所有数据集中的对象总数不能超过 **30,000,000 个对象**。
- **将对象加载到内存（OSDK 限制）：** 在本体 SDK 中使用 `.all()` 或 `.allAsync()` 方法加载对象时，上限为 **100,000 个对象**，以防止内存耗尽和函数超时。你可以使用 `getAllObjects` API 端点加载更多对象。

> **ℹ️ 提示**
>
> 在对象函数中加载超过 10,000 个对象可能会导致执行超时，具体取决于函数逻辑的复杂度。请考虑使用分页或筛选来减小对象集大小。

## 理解环绕搜索结果集

当你执行环绕搜索操作来遍历对象之间的链接关系时，OSS 会使用一种特殊的连接操作类型来高效地查找相关对象。

例如，当你从一组客户对象出发，通过链接关系搜索所有相关的订单对象时：

- **起始集**是你的客户对象（你从中发起搜索的对象）
- **结果集**是与这些客户链接的订单对象（你搜索所指向的对象）

OSS 使用左半连接（left-semi join）来实现环绕搜索操作，它只返回结果集中具有匹配链接的对象，而不会复制起始集中的数据。10,000,000 个对象的限制适用于这个结果集——即遍历链接关系后返回的所有不重复对象的总集合。

## 在 OSS 限制内工作的最佳实践

为确保最佳性能并避免触及大小限制：

- **尽早筛选：** 在执行连接或将对象加载到内存之前，先应用筛选以减小对象集大小。OSS 会利用已编入索引的数据结构，使筛选后的查询更高效。
- **避免无法利用索引的操作：** 对派生属性和计算 SQL 列进行筛选、聚合、排序以及其他操作，需要对所有行求值，无法使用内部索引。这些操作不会走快速下推路径，即使对于小对象集也可能触发内存或 Spark 执行。例如，如果你想筛选 2026 年 5 月发生的所有订单，应避免使用 `(MONTH FROM order_date) = 'May' AND (YEAR FROM order_date) = '2026'`。而应使用范围筛选：`order_date > '2026-05-01' && order_date < '2026-06-01'`。
- **使用分页：** 在对象函数中处理大对象集时，使用分页模式分批处理对象，而不是一次性加载所有对象。
- **监控对象集大小：** 在执行环绕搜索等昂贵操作之前，使用聚合查询来了解对象集的大小。环绕搜索操作的计算开销很大，这正是 OSS 实施这些大小限制的原因。
- **优化数据模型：** 如果你频繁触及大小限制，请考虑使用传统数据建模原则重构你的本体。通过将相关数据合并到对象属性中来对本体进行反规范化，可以减少对昂贵环绕搜索操作的需求，使查询更高效。你还可以创建更有针对性的对象类型或链接关系，它们自然会产生更小的结果集。
- **考虑计算成本：** 基于 Spark 的执行比内存执行使用更多计算资源。触发 Spark 回退的查询将消耗额外的[计算秒](https://www.palantir.com/docs/foundry/ontologies/query-compute-usage/)。

> **ℹ️ 提示**
>
> OSS 使用大小估算来决定是否执行查询。如果估算大小显著超过限制（超过 2 倍），查询可能在达到确切阈值之前就失败。这是一项性能优化，用于避免昂贵的精确计数操作。
