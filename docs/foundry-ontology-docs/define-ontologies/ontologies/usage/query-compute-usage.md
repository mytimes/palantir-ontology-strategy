# 本体查询的计算用量（Compute usage with Ontology queries）

> 本文为 [Palantir 官方文档](https://www.palantir.com/docs/foundry/ontologies/query-compute-usage/)的非官方中文翻译，仅供学习参考。原文 © 2026 Palantir Technologies Inc. 保留所有权利。

Foundry 本体是一个数据后端，它将基于文件的数据映射为以组织为中心的对象，并为数据探索、数据分析、运营数据编辑、场景分析等提供高速查询服务。本体将数据存储在多模态存储后端中，每个后端都有其各自的用途，并且可以在单个请求中灵活查询。查询 Foundry 本体需要了解下面讨论的一些基础概念。

> **ℹ️ 提示**
>
> 如果你与 Palantir 签有企业合同，请在进行计算用量计算之前联系你的 Palantir 代表。

## 核心概念：对象类型与对象集

第一个重要概念是**对象类型**与其对应的**对象集**之间的区别。**对象类型**是实体本身的语义表示（例如对象的名称和属性）。

一个对象类型有对应的**对象集**，其中包含对象本身。**对象集**的大小对应于输入数据集的行数，以及由本体动作创建和删除的对象数量。

## 核心概念：查询类型

第二个重要概念是**查询类型**，包括筛选、聚合、环绕搜索（Search Around）和回写操作。每种查询类型的执行都需要计算。有关每种查询类型当前的计算秒开销，请参阅[本体查询计算（2026）](#本体查询计算2026)。

使用 Foundry 本体时，**查询类型**由以下 [Foundry 应用](https://www.palantir.com/docs/foundry/ontology/applications/)针对**对象集**执行：

- Object Explorer
- Workshop
- Quiver
- Slate
- Vertex
- Foundry Rules
- Foundry Machinery
- 对象 API（OPI）

从上述任何来源查询本体都会消耗计算秒来运行查询。

## 调查本体查询产生的 Foundry 计算用量

在 Foundry 中，计算秒归属到平台中的资源，而不是与这些资源交互的用户。

对于本体查询，计算有多种归属方式。一般规则是，计算附加到查询发起所在的资源。但是，当不存在用于产生该计算的已保存资源时（例如通过 API），计算将附加到被查询的对象类型。如果在单个请求中查询了多个对象，则计算在这些对象之间平均分摊。

以下资源类型的本体查询计算归属到资源本身，而不是底层对象：

- Workshop 应用
- Carbon 页面
- Quiver 分析和仪表板
- Vertex 应用
- Slate 应用
- Foundry Machinery 应用
- Foundry Rules 资源
- Foundry Automate
- AIP Logic
- SQL Console 工作表
- OSDK 应用

以下交互模式的本体查询计算直接附加到它们所查询的对象类型，因为没有可以附加计算的既定资源。

- Object Explorer
- 对象 API（包括 OSDK）

## 本体查询计算（2026）

> **ℹ️ 提示：自 2026 年 1 月 1 日起生效**
>
> 以下计算模型于 2026 年 1 月 1 日生效，并取代下文[旧版](#使用本体对象查询度量-foundry-计算-旧版)一节中描述的旧模型。

本体查询计算由用户和智能体对本体的使用驱动。决定计算用量的主要因素包括：

### 因素 1：用户和智能体数量

计算秒是累计度量的。针对本体运行的查询和转换越多，总体计算用量就越高。查询量随用户交互（例如应用刷新和交互式查询）以及智能体转换线性增长。

### 因素 2：查询类型

用户可以通过以下查询类型访问其本体，每种类型都有每次查询的最低计算秒开销。实际计算用量可能更高，具体取决于查询复杂度、对象集大小或被查询对象的数量。

- **基础查询：** 原样返回对象集，或对某些属性进行基础筛选。
- **环绕搜索查询：** 接收一个输入对象集，并基于输入集的某个属性在另一个对象集上运行次级筛选。
- **聚合查询：** 接收一个输入对象集，并对该集中所有对象的某个属性运行聚合函数（例如 `sum` 或 `avg`）。
- **[本体 SQL 查询](https://www.palantir.com/docs/foundry/sql-warehousing/ontology-sql)：** 使用标准 Spark SQL 语法，直接针对对象存储中的对象类型、链接和接口运行 SQL 查询。
- **高级查询：** 其他查询类型未涵盖的任何情况。例如，对整个对象集的嵌入运行语义搜索。
- **派生属性查询：** 派生属性是在运行时根据对象上其他属性或链接的值计算出的属性，包括对链接对象的属性进行聚合或选取。派生属性随后可在同一请求中用于筛选、排序或聚合等进一步操作。
- **动作：** 回写操作，替换指定对象集中对象的属性值。动作的最低开销为 `18` 计算秒，并随被编辑对象的数量扩展：除第一个对象外，每编辑一个对象额外产生 `1` 计算秒。
- **本体计算（Phonograph）[旧版]：** 针对仍使用对象存储 v1（OSv1）后端的对象的查询。这些查询在资源管理应用中显示为 “Ontology Compute (phonograph)”。针对这些查询仍保留[现有 OSv1 计算模型](#使用对象存储-v1-度量计算-旧版)。

**下表总结了每种查询类型的最低计算秒开销。**

| 查询类型 | 最低计算秒开销 |
| --- | --- |
| 基础查询 | 2 |
| 环绕搜索查询 | 5 |
| 聚合查询 | 5 |
| 本体 SQL 查询 | 5 |
| 高级查询 | 10 |
| 派生属性查询 | 10 |
| 动作 | 18 |
| 本体计算（Phonograph）[旧版] | 16 |

> **ℹ️ 提示**
>
> 对象存储 v1（OSv1）查询的现有计算模型已保留。针对仍使用 OSv1 后端的对象的任何查询，每次查询的最低开销为 `16` 计算秒。

## 使用本体对象查询度量 Foundry 计算 [旧版]

> **ℹ️ 提示：旧版**
>
> 以下各节描述 2026 年 1 月 1 日之前生效的旧计算模型，保留以供参考。有关当前计算模型，请参阅上文的[本体查询计算（2026）](#本体查询计算2026)。

在旧模型下，查询本体按以下方式消耗计算秒：

- 用于查询开销的固定最低计算秒数。
- 额外的、按规模扩展的计算秒数，按服务该查询所消耗的计算量度量。

### 使用对象存储 v1 度量计算 [旧版]

对象存储 v1（Phonograph）将数据存储在持久化、水平可扩展集群中的一组分布式索引里。在这些索引中，数据位于大型数据结构中，由本体查询引擎遍历。执行查询时，引擎可以通过遍历索引，在搜索过程中避免处理大片数据。这个过程称为“剪枝（pruning）”。

使用该引擎，你可以在数十亿条记录中搜索，而实际求值的记录数最多可减少至千分之一。对一条记录的每次物理求值称为一次“命中（hit）”。对象存储 v1 的设计目标是最小化每次查询中的命中数。

### 使用对象存储 v2 度量计算 [旧版]

对象存储 v2（OSv2）以 Palantir 优化的增强索引格式存储对象，专为高速索引构建、环绕搜索和回写而优化，也便于向多个计算后端顺畅交接以完成复杂任务。这包括作为查询一部分的完全并行化 Spark 计算。

鉴于对象存储 v2 也使用高效的索引结构，对象存储 v1 中关于**命中**的原则同样适用于基础查询。不过，作为查询一部分而启动的按需 Spark 容器也可能消耗计算秒。

对对象存储 v2 后端中的对象发起的查询，按以下模式消耗计算：

- 对于对象存储 v1 后端中的对象，每次查询的最低计算秒开销为 `16` 计算秒。
- 对于对象存储 v2 后端中的对象，每次查询的最低计算秒开销为 `4` 计算秒。对象存储 v2 的优化结构所需开销低于对象存储 v1，因此其最低计算秒开销更低。
- 当进程在查询的剪枝过程中执行计算工作时，需要额外的计算秒。额外的计算秒随索引中的对象数量以及查询类型而扩展。
- 在对象存储 v2（OSv2）中，索引剪枝同样需要额外的计算秒。不过，当对超过 100,000 个对象运行环绕搜索，或在单个请求中对超过 10,000 个对象运行回写操作时，OSv2 还支持按需 Spark 集群搜索。这些 Spark 集群以与平台上所有其他基于 Spark 的应用相同的方式消耗用量。有关说明，请参阅[并行化计算文档](https://www.palantir.com/docs/foundry/resource-management/usage-types/)。
- 回写到本体的动作具有最低开销。每个动作有 `18` 计算秒的开销。动作还会随回写请求中被编辑对象的数量扩展：除第一个对象外，每编辑一个对象额外产生 `1` 计算秒。
- 通过对象函数（Functions on Objects）运行的函数具有最低开销。具体而言，每次函数执行有 `4` 计算秒的固定开销。

**下表总结了旧模型下每种查询类型的最低计算秒用量。**

| 查询类型 | 最低计算秒 |
| --- | --- |
| 本体 V1 查询 | 16 |
| 本体 V2 查询 | 4 |
| 对象动作 | 18 |
| 对象函数 | 4 |

## 理解本体查询的 Foundry 计算用量驱动因素 [旧版]

- 一条非常简单的规则是：每次查询的固定计算用量随查询数量线性增长。执行更少的查询，聚合起来消耗的计算就更少。
- 发往对象集服务的更复杂查询（例如通用的多对象搜索）会向每个对象类型发起多个子查询。将搜索限制在单个对象类型上，可以减少你使用的查询数量。
- 对较小对象集的查询比对较大对象集的查询消耗更少计算，因为查询中的**命中**数与被查询对象集的大小成正比。
- 在执行其他操作之前预先筛选，可以充分利用高度索引化的后端结构。这将减少查询中的**命中**数，从而降低总体计算用量。这对于聚合和环绕搜索尤其重要，因为经过筛选的对象集比完整对象集处理起来需要更少计算。
