# 函数版本管理（Function versioning）

> 本文为 [Palantir 官方文档](https://www.palantir.com/docs/foundry/functions/functions-versioning/)的非官方中文翻译，仅供学习参考。原文 © 2026 Palantir Technologies Inc. 保留所有权利。

本文介绍函数所使用的版本管理系统。函数的发布版本由发布者选择，创建后不可变。采用恰当的版本号对于为函数的使用者提供稳定、可靠的体验至关重要。

## 向后兼容的变更与破坏性变更

函数的版本管理系统区分向后兼容的变更和破坏性变更。*向后兼容的变更*（backward compatible changes）是指不会干扰函数现有使用者的变更。不向后兼容的变更可称为*向后不兼容*（backward incompatible）变更或*破坏性*（breaking）变更。

向后兼容变更的一些例子：

- 为函数签名添加一个可选输入。
- 在不改变预期行为的前提下优化函数性能。
- 在不改变预期行为的前提下修复函数中的 bug。

破坏性变更的一些例子：

- 为函数签名添加一个必填输入。
- 将函数签名的输出类型从整数改为字符串。
- 删除一个函数。

在判断对现有版本的某项变更是否向后兼容时，问问自己：该变更是否会对现有版本的使用者造成干扰，或需要他们显式处理。

请记住，函数的预期使用方式最终由你决定。

## 语义化版本管理系统

函数按照[语义化版本（Semantic Versioning）↗](https://semver.org/)系统进行版本管理。

在语义化版本中，版本号采用 `X.Y.Z` 的形式，其中 `X`、`Y`、`Z` 分别为主版本号、次版本号和补丁版本号，均为非负整数（例如 `1.2.3`）。版本号还可以在补丁版本号之后紧接一个连字符，附加由字母数字字符组成的预发布标识符（例如 `1.2.3-rc1`）。

> **ℹ️ 提示**
>
> 本页仅对语义化版本做简要总结。我们建议你阅读[完整规范 ↗](https://semver.org/)，因为遵守该规范是发布可被其他应用可靠使用的函数的重要一环。

### 选择发布版本号

发布函数的新版本时，请考虑语义化版本规范中的以下要点：

- 主版本号 `0`（`0.y.z`）用于初始开发阶段。在初始开发期间，函数可能随时变化，使用者不应认为你的函数已经稳定。
- 做出向后不兼容的变更时，应递增主版本号。
- 以向后兼容的方式添加功能时，应递增次版本号。
- 做出向后兼容的 bug 修复时，应递增补丁版本号。
- 预发布版本表示该版本不稳定，可能不满足其关联的正式版本所标明的兼容性要求。

### 向后兼容性检查

在你发布新版本之前，系统会对你的函数执行向后兼容性检查。具体而言，以下破坏性变更都会触发警告：

- 移除函数，包括在 Python 或 TypeScript 函数代码仓库中删除函数。
- 移除函数签名中的某个输入（即使是可选输入）。
- 调整函数签名中输入的顺序。
- 为函数签名添加必填输入。
- 不当的输入类型变更（例如从整数改为字符串）。注意，放宽数值输入类型（如从整数改为浮点数）会产生警告。
- 不当的输出类型变更（例如从字符串改为可选字符串）。

如果这些检查因任何原因失败，建议你发布一个主版本。但如果你仍处于初始开发阶段（即主版本号仍为 `0`），则不适用此建议。

> **⚠️ 注意**
>
> Palantir 内置的检查并不能穷尽所有类型的破坏性变更。例如，内部实现导致的破坏性变更可能无法被检测到。仅因这些检查通过就发布次版本或补丁版本是不安全的。

#### 注意事项：自定义类型

函数内部数据类型表示目前缺少关于自定义类型字段可选性的充分信息。因此，你可能会注意到：对于自定义类型的输入和输出，在移除或添加任何字段时（包括可选字段，如 TypeScript 中的 `quantity?: Integer` 或 Python 中的 `quantity: Integer = 0`），向后兼容性检查都会发出警告。

我们正在进行改进，今后在输出自定义类型上移除可选字段、或在输入自定义类型上添加可选字段时，将不再发出警告。

> **ℹ️ 提示**
>
> 在输入自定义类型上移除可选字段时，你仍会收到警告。忽略使用者提供的任何字段通常被视为不良做法，因为使用者很可能期望所提供的字段能决定函数的行为。

### 限制稳定版本标签

如果下游生产应用已配置为通过版本范围（例如 `>=1.2.3 <2.0.0`）引用函数，那么稳定的语义化版本发布（非预发布版本）可能会立即被这些应用使用。因此，在以新的稳定版本发布代码变更之前，对其进行评审和测试非常重要。

你可以在代码仓库设置中[启用一个开关](https://www.palantir.com/docs/foundry/code-repositories/branch-settings/#restrict-stable-version-tags)，将函数稳定版本的发布限制在受保护分支上。

## 常见问题

### 在 0.y.z 初始开发阶段如何选择发布版本号

常见做法是：任何破坏性变更都放在次版本发布中，任何向后兼容的变更都放在补丁版本发布中。这是许多开发领域（如 Node/NPM 生态）的使用者所做的假设，[脱字符范围（caret ranges）↗](https://docs.npmjs.com/cli/v6/using-npm/semver#caret-ranges-123-025-004)的广泛使用就证明了这一点。

### 意外地以补丁版本或次版本发布了向后不兼容的变更

一旦你意识到自己发布了破坏性变更，就应尽快修复问题，并在一个新的次版本中恢复向后兼容性。

请看以下示例。

1. 你有一个名为 `myFunction` 的函数，版本为 `1.0.0`，接收单个字符串输入。
2. 你为 `myFunction` 添加了一个新的必填输入，并意外地在次版本 `1.1.0` 中发布了这一变更。

要补救此问题，你可以撤销对签名的破坏性变更（即移除你在 `1.1.0` 中添加的新必填输入），并在版本 `1.2.0` 中发布这一变更。

### 当发布失败或尚未发布时如何检查向后兼容性

对于 TypeScript 或 Python 函数，函数可能会发布失败，或需要几分钟才能发布完成。在这两种情况下，内置的向后兼容性检查都无法运行。如果你想在进行新的发布之前查看这些检查的结果，有以下选择：

- 如果上一次发布失败，你应使用“自定义标签”选项与上一个成功的标签进行比较。
- 如果上一次发布尚未发布，你应等待其完成。
